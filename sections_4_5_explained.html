סעיף 4: איכות הנתונים

ההנחיות שואלות שלוש שאלות: האם יש נתונים חסרים, האם יש נתונים לא הגיוניים, ואם יש תובנות נוספות על הנתונים. ענינו עליהן בארבעה שלבים, והוספנו שלב רביעי: האם הנתונים עקביים לאורך השנים. בסעיף 4 לא משנים כלום ב-df. רק בודקים ומחליטים, והביצוע נעשה בסעיף 5.

4.1 ערכים חסרים, כפילויות וימים חסרים

print(df.isna().sum().to_string())                                   # missing values per column
print(df.duplicated(subset=["location", "date"]).sum())              # duplicate (city, day) rows
print(df["location"].value_counts().sort_index().to_string())        # days per city
  • isna().sum(): לכל עמודה, כמה ערכים חסרים (NaN) יש בה.
  • duplicated(subset=[...]): מסמן שורות שיש להן עיר ותאריך שכבר הופיעו קודם.
  • value_counts(): כמה ימים יש לכל עיר. אם בכל העיר יש אותו מספר, לא חסרים ימים שלמים.

התוצאה: 0 ערכים חסרים בכל העמודות, 0 כפילויות, ו-6,154 ימים לכל עיר. את הרצף של התאריכים בדקנו כבר בסעיף 2.

למה זה יצא נקי: הנתונים הם פלט של מודל (reanalysis). המודל מחשב ערך לכל שעה ולכל נקודת רשת, אז אין חיישן שמתקלקל ואין חור בנתונים.
החלטה: אין מה להשלים ואין שורות להסיר. הערה לחלק ב': אם בקובץ JSON של המבחן יופיע ערך ריק (null), הוא יהפוך ל-NaN, ולכן כדאי לבדוק את זה לפני החיזוי.

4.2 בדיקות היגיון

לכל בדיקה בונים "מסכה": עמודה של True/False, שבה True אומר שהשורה מפרה את הכלל. אחר כך סופרים את ה-True.

checks = {
    "min temperature > max temperature":
        df["temperature_2m_min"] > df["temperature_2m_max"],
    "mean temperature outside [min, max]":
        ~df["temperature_2m_mean"].between(df["temperature_2m_min"], df["temperature_2m_max"]),
    ...
    "precipitation without hours, or hours without precipitation":
        (df["precipitation_sum"] > 0) != (df["precipitation_hours"] > 0),
    ...
}
check_table = pd.Series({name: int(mask.sum()) for name, mask in checks.items()}, name="rows")
  • ~ הופך True ל-False ולהפך. לכן ~between(...) פירושו "מחוץ לטווח".
  • (A > 0) != (B > 0): True כשבדיוק אחד מהשניים חיובי, למשל ירד גשם אבל לא נרשמה אף שעת משקעים.
  • mask.sum(): True נספר כ-1, ולכן הסכום הוא מספר השורות שמפרות את הכלל.

4.4 האם הנתונים עקביים לאורך זמן? (הממצא החשוב של הסעיף)

הרקע: מהתיעוד ידוע שברירת המחדל משלבת כמה מודלים: ERA5 ו-ERA5-Land, ‏IFS מ-2017, ולפי התיעוד גם מערך נתונים חדש של IFS מ-2024. השאלה: אם המודל מתחלף, משתנה יכול "לקפוץ" בלי שמזג האוויר השתנה. בדקנו ממוצעים שנתיים לכל עיר.

year = df["date"].dt.year
yearly_wind = df.groupby([year, "location"])["wind_speed_10m_max"].mean().unstack()
is_trace = (df["precipitation_sum"] > 0) & (df["precipitation_sum"] < RAIN_THRESHOLD_MM)
yearly_trace = is_trace.groupby([year, df["location"]]).mean().unstack()

groupby([year, "location"]) מקבץ לפי שנה ועיר. unstack() הופך את העיר לעמודות, כך שיש טבלה של שנה × עיר שאפשר לצייר כקו לכל עיר. "יום trace" הוא יום עם קצת משקעים, אבל פחות מ-1 מ"מ.

רוח במ"ש לשעה, ממוצע המקסימום היומי.

  • ינואר 2017: מהירות הרוח קופצת בכל הערים בבת אחת. בטוקיו היא עולה מ-21 קמ"ש בדצמבר 2016 ל-30 קמ"ש בינואר 2017. מזג אוויר לא משתנה כך בחודש אחד בשש ערים, ולכן זה המודל. גם אחוז ימי ה-trace עולה: המודל החדש מייצר יותר טפטוף קל.
  • סוף 2024: הרוח יורדת שוב, ובחלק מהערים אפילו מתחת לרמה הישנה. בטוקיו: 25 קמ"ש באוקטובר 2024, ו-13–14 קמ"ש מדצמבר 2024.

  • כיוון הרוח בוונקובר: התמהיל של הכיוונים השתנה ב-2017. למשל דרום-מזרח ירד מ-27% ל-17%, ומערב עלה מ-7% ל-18%. אבל דפוס הגשם נשמר: רוח מזרחית היא הגשומה ביותר בשתי התקופות (76% ו-71%). כלומר, הממצא מסעיף 3.5.3 אמיתי ולא תוצר של מודל אחד.
למה זה חשוב: מודל לומד קשר בין ערכים של מאפיינים לבין המטרה. אם אותו מזג אוויר מקבל מהירות רוח שונה לפי השנה, המודל לומד ערבוב של שתי סקאלות. ובנוסף, המבחן בחלק ב' יגיע מהמודל החדש ביותר, מאחרי 2024, שנראה שונה מרוב שנות האימון שלנו. זה סוג של distribution shift (שינוי בהתפלגות) שנגרם ממקור הנתונים ולא ממזג האוויר. זה ממצא לא טריוויאלי, ושווה להבליט אותו בדוח לבונוס.

סעיף 5: הכנת הנתונים

שני כללים לכל הסעיף:

  1. כל מאפיין מחושב מיום אחד בלבד, היום שממנו חוזים. לא משתמשים בימים קודמים (lag או ממוצע נע), כי עוד לא יודעים אם דוגמת מבחן בחלק ב' תכיל יותר מיום אחד. זו השאלה הפתוחה למתרגל. אם יתברר שכן, אפשר להוסיף מאפייני עבר אחר כך.
  2. שום דבר לא "נלמד" מהנתונים: אין ממוצעים, אין נרמול ואין ספים שמחושבים מהנתונים. כל צעד הוא כלל קבוע. לכן אותו קוד נותן אותה תוצאה על כל הטבלה ועל קובץ JSON בודד, ואין דרך שמידע מימים אחרים או מהעתיד ידלוף. נרמול, אם מודל ידרוש אותו, שייך לחלק ב', ושם הוא נעשה רק על סט האימון.

כל הצעדים נמצאים בפונקציה אחת, make_features, כדי שבחלק ב' אפשר יהיה להריץ אותה על קובצי JSON של המבחן.

5.3 פונקציית המאפיינים, חלק אחרי חלק

קבוצת מזג האוויר: פונקציה רגילה עם תנאים לפי טווחים, כדי שכל קוד אפשרי יקבל קבוצה:

def weather_group(code):
    if code <= 2:
        return "clear"
    if code <= 48:          # 3 overcast, 45/48 fog
        return "overcast"
    ...
    return "rain"           # 95-99 thunderstorm

One-Hot עם רשימת קטגוריות קבועה:

def one_hot(values, categories, prefix):
    dummies = pd.get_dummies(pd.Categorical(values, categories=categories), prefix=prefix, dtype=int)
    dummies.index = values.index
    return dummies

get_dummies יוצר עמודה של 0/1 לכל ערך. הבעיה: על יום מבחן בודד, למשל בלונדון, הוא היה יוצר רק עמודה אחת, city_london, ולמודל חסרות חמש עמודות. הפתרון: pd.Categorical(..., categories=...) מגדיר מראש את כל הקטגוריות האפשריות, ולכן תמיד נוצרות כל העמודות. השורה dummies.index = values.index מוודאת שהשורות מתיישרות עם הטבלה המקורית.

משקעים:

out["rain_today"] = (precip >= RAIN_THRESHOLD_MM).astype(int)
out["snow_today"] = ((precip - days["rain_sum"]) > 0.05).astype(int)
precip_cat = np.select([precip == 0, precip < RAIN_THRESHOLD_MM, precip < 10],
                       ["dry", "trace", "moderate"], default="heavy")

np.select עובר על התנאים לפי הסדר ונותן לכל שורה את הקטגוריה של התנאי הראשון שמתקיים. אם אף תנאי לא מתקיים, השורה מקבלת את default. לכן "פחות מ-10" תופס רק את מה שלא נתפס כבר כ-0 או כפחות מ-1.

טמפרטורה: temperature_mean, ו-temp_range שהוא המקסימום פחות המינימום.

כיוון הרוח כנקודה על מעגל:

direction = np.deg2rad(days["wind_direction_10m_dominant"])
out["wind_dir_sin"] = np.sin(direction)     # east (+1) / west (-1)
out["wind_dir_cos"] = np.cos(direction)     # north (+1) / south (-1)

במקום מספר אחד בין 0 ל-360, כל כיוון הופך לשני מספרים, הנקודה שלו על מעגל. כך 359° ו-1° יוצאים כמעט זהים: ‏(‎-0.02, 1.00) ו-(0.02, 1.00). deg2rad ממיר ממעלות לרדיאנים, כי sin ו-cos עובדים ברדיאנים. בחרנו בכיוון לבד ולא ברכיבי u/v, כי u/v כוללים את מהירות הרוח, שהיא לא יציבה (4.4).

חודש ועונה:

month = days["date"].dt.month
out["month_sin"] = np.sin(2 * np.pi * month / 12)
out["month_cos"] = np.cos(2 * np.pi * month / 12)
season = month.map(NORTHERN_SEASON)
season = season.where(~days["location"].isin(SOUTHERN_HEMISPHERE), season.map(OPPOSITE_SEASON))

החודש הופך לנקודה על מעגל באותו אופן כמו הרוח, כך שדצמבר וינואר יוצאים קרובים. העונה נקבעת לפי חצי הכדור הצפוני. where אומר: "השאר את הערך במקום שבו התנאי נכון, ובשאר המקומות קח את הערך השני". בסידני, שבה התנאי לא נכון, העונה מתהפכת: ינואר הופך לקיץ.

מ-JSON לטבלה:

def json_to_days(payload, location):
    days = pd.DataFrame(payload["daily"]).rename(columns={"time": "date"})
    days["date"] = pd.to_datetime(days["date"])
    days["location"] = location
    return days

אותו דבר ש-sensing.py עושה לכל קובץ, אבל לקובץ בודד. את העיר מעבירים כפרמטר, כי ה-JSON מכיל רק קואורדינטות.

5.4 בדיקת המאפיינים: Mutual Information

Mutual Information (MI) מודד כמה ידיעת מאפיין מקטינה את אי-הוודאות לגבי המטרה. בניגוד למתאם, הוא תופס גם קשרים שאינם קו ישר. 0 אומר "אין מידע". צירפנו להשוואה גם את המשתנים הגולמיים שהוצאנו, באפור.

is_discrete = (X_all.nunique() <= 2).to_numpy().copy()     # 0/1 columns
mi = mutual_info_classif(X_all, y, discrete_features=is_discrete, random_state=42)

צריך לספר לפונקציה אילו עמודות בדידות (0/1), כי היא מחשבת אותן בשיטה אחרת. random_state=42 קובע את האקראיות של החישוב, כך שהתוצאה תצא זהה בכל הרצה.

5.5 האם הפונקציה עובדת על JSON גולמי?

בחלק ב' נקבל קובצי JSON גולמיים. כדי לבדוק, לקחנו קובץ אמיתי, data/raw/london_2026.json, הוצאנו ממנו יום אחד (6.11.2026), הרצנו עליו את json_to_days ואחריה make_features, הורדנו את FEATURES_TO_DROP, והשווינו לאותו יום בטבלה.

pd.testing.assert_frame_equal(from_json, from_table, check_dtype=False)

assert_frame_equal עוצר את המחברת עם שגיאה אם יש הבדל כלשהו, ולכן אם המחברת רצה עד הסוף, הבדיקה עברה. check_dtype=False מתעלם מהבדלים כמו 4 לעומת 4.0. התוצאה: אותן 33 עמודות ואותם ערכים. בנוסף בדקנו שקוד 95 (סופת רעמים), שלא מופיע בנתונים שלנו, מקבל את הקבוצה rain.
